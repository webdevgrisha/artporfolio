# Архитектура

Как устроен проект и каким соглашениям следует каждое изменение. Правила CSS — в [STYLE_GUIDE.ru.md](STYLE_GUIDE.ru.md).

## Обзор

Монорепозиторий pnpm из двух пакетов, развёрнутых в Firebase:

| Пакет | Стек | Где работает |
| --- | --- | --- |
| `front` | React 19, React Router (data mode), TanStack Query, react-hook-form, Vite, CSS Modules, zod | Firebase Hosting |
| `backend` | Express 5, Firebase Admin, zod | Cloud Functions (`api`, europe-west1) |

Firebase Hosting отдаёт фронтенд и перенаправляет `/api/**` в функцию `api`, поэтому браузер работает с одним источником (origin).

## Фронтенд: Feature-Sliced Design

`front/src` построен по [Feature-Sliced Design](https://feature-sliced.design). Код разделён на **слои**; слой может импортировать только из слоёв **ниже** себя.

| Слой | Что содержит | Пример |
| --- | --- | --- |
| `app` | Точка входа, роутер, глобальные стили | `app/router.tsx` |
| `pages` | По слайсу на маршрут; собирает виджеты и фичи | `pages/login` |
| `widgets` | Крупные самостоятельные блоки интерфейса | `widgets/admin-layout` |
| `features` | По одному действию пользователя | `features/login`, `features/logout` |
| `entities` | Бизнес-сущности: модель данных, запросы, UI только для чтения | `entities/user` |
| `shared` | Код без знания о предметной области | `shared/ui/button`, `shared/api/http` |

### Слайсы и сегменты

Каждый слой, кроме `app` и `shared`, состоит из **слайсов**, названных по бизнес-понятию в kebab-case. Внутри слайса код сгруппирован по **сегментам**:

| Сегмент | Назначение |
| --- | --- |
| `ui` | Компоненты и их CSS Modules |
| `model` | Состояние, хуки, loader и action маршрутов, схемы |
| `api` | Запросы к бэкенду или Firebase |
| `lib` | Чистые вспомогательные функции |

```text
features/login/
├── api/        createSession, signInWithFirebase
├── lib/        getLoginErrorMessage
├── model/      login, loginSchema
├── ui/         LoginForm.tsx, LoginForm.module.css
└── index.ts    публичный API
```

### Правила импортов

Проверяются Biome (`noRestrictedImports` в `biome.json`):

- Слайс импортируется только через свой публичный `index.ts`: `@/features/login`, а не `@/features/login/model/login`.
- Слой импортирует только из нижних слоёв: `features` может использовать `entities` и `shared`, но не `widgets` и не `pages`.
- `app` не импортирует никто.
- Внутри одного слайса импорты относительные (`../model/login`). Между слайсами и слоями — через алиас `@/`.
- Слайсы одного слоя не импортируют друг друга. Общее опускается на слой ниже (`isSessionExpiredError` нужен нескольким фичам, поэтому лежит в `shared/api`).

В `shared` слайсов нет. У каждого компонента `shared/ui` свой публичный `index.ts` (`@/shared/ui/button`). `shared/api`, `shared/config` и `shared/lib` импортируются по файлам (`@/shared/api/http`) намеренно: общий index заставил бы каждый чанк, которому нужен HTTP-клиент, загружать ещё и Firebase.

### Именование

- Папки слайсов и компонентов `shared/ui`: kebab-case (`admin-layout`, `password-input`).
- Файлы компонентов: PascalCase, один компонент на файл, CSS Module рядом (`LoginForm.tsx`, `LoginForm.module.css`).
- Остальные файлы: camelCase, по смыслу содержимого (`getCurrentUser.ts`, `toast.ts`, `contactsRoute.ts`).
- Компоненты страниц заканчиваются на `Page` (`GalleryPage`).

### Маршруты и данные

- Пути и заголовки навигации админки заданы один раз в `shared/config/routes.ts`.
- `app/router.tsx` сопоставляет пути со страницами, которые загружаются лениво.
- Данные загружаются через loader React Router, а не через эффекты. Action используется только для изменения, после которого открывается другая страница:
  - маршрут лейаута админки вызывает `requireSession` (`entities/user`) при каждом переходе; на 401 он перенаправляет на `/admin/login?redirectTo=…`, и этот редирект важнее упавшего loader страницы. Любой другой сбой — ошибка, а не повод входить заново;
  - внутри админки `useSessionUser()` возвращает текущего пользователя;
  - у страницы входа свои loader и action в `pages/login/model/loginRoute.ts`;
  - выход — это `<Form method="post">` на action `/admin/logout` (`features/logout`). Если сессия могла остаться (нет связи, запрос отклонён), action показывает тост с ошибкой и возвращает на страницу, с которой отправлена форма. После ошибки сервера он сначала спрашивает `/auth/me`: сервер мог очистить cookie и не суметь только отозвать сессию, а мог ответить прокси, и тогда запрос до сервера не дошёл;
  - данные сервера хранятся в кэше TanStack Query (`queryClient` в `shared/api/queryClient.ts`). Сущность отдаёт каждый запрос как query options (`contactsQuery` в `entities/contacts`). Фоновых перезапросов нет: данные меняет только админка;
  - страница редактирования загружает данные заново при каждом входе: её loader вызывает `queryClient.fetchQuery` (`pages/contacts/model/contactsRoute.ts`), а страница читает их через `useSuspenseQuery` и передаёт форме;
  - форма остаётся на странице, поэтому сохраняет в обработчике отправки react-hook-form (`EditContactLinksForm`) через хук мутации (`useSaveContactLinks`). Мутация отправляет изменения и инвалидирует запрос страницы после каждого сохранения, в том числе неудачного: упавший запрос мог всё же изменить данные на сервере. Затем форма сбрасывается к сохранённым значениям и показывает результат. Пока идёт сохранение, `isSubmitting` блокирует форму;
  - при выходе кэш запросов очищается.
- Каждое изменение несёт CSRF-токен, и вызывающему коду об этом знать не нужно: `http` (`shared/api/http.ts`) запрашивает его через `GET /api/auth/csrf` при первом изменении и дальше использует повторно. Ответ 403 значит, что сессия сменилась, например после повторного входа в другой вкладке: `http` получает новый токен и отправляет изменение ещё раз. Вход отправляется без токена (`withCsrfToken: false`), при выходе токен забывается.
- `PageLoading` — это `HydrateFallback`, который виден, пока выполняются первые loader.
- Корневой маршрут без пути ловит через `ErrorPage` (`pages/error`) любую ошибку, которую не обработал маршрут ниже. Он импортируется сразу, а не лениво, поэтому работает и когда не загрузился чанк.
- Страницы админки вложены в маршрут без пути, у которого `ErrorBoundary` — `AdminPageError` (`widgets/admin-layout`): страница, которая не загрузилась или упала при рендере, заменяется сообщением внутри лейаута, а навигация продолжает работать.

### Формы и обратная связь

- Формы построены на react-hook-form со схемой zod, которая повторяет правила сервера. Текстовые поля (`Input`, `Textarea`) построены на `Field` (`shared/ui`), который отвечает за подпись, подсказку (`hint`), ошибку и рамку; изменённые поля подсвечиваются пропом `isModified`.
- Форма редактирует один ресурс API и сохраняет все свои изменения или ни одного. Если на странице несколько ресурсов, каждый получает свой раздел: дочерний маршрут со своим адресом и формой (`pages/about`: `/admin/about/text`, `/photo`, `/process`). Страница — это маршрут-лейаут: её loader загружает данные один раз, а `TabNav` (`shared/ui`) связывает разделы ссылками, оформленными как вкладки. Переключение раздела — это переход, поэтому несохранённые изменения всегда в открытом разделе, а уход из него сначала спрашивает, как уход с любой страницы.
- Файлы выбираются через `MediaPicker` (`shared/ui`), по одному файлу. Он проверяет тип и размер по переданным правилам (`rules={imageUploadRules}`) и показывает миниатюры, которые открываются в `PreviewDialog`, но ничего не загружает: в форме выбранный `File` хранится и отправляется при сохранении, поэтому на него тоже действуют отмена изменений и защита от ухода со страницы; поле, которое сохраняется само по себе, загружает файл сразу и на это время показывает `isBusy`. Правила загрузки (`imageUploadRules`) и изображение, которое возвращает API (`imageSchema`), лежат в `shared/api/image`. Одно сохранённое изображение в форме, например фото с alt, выбирается через `ImagePicker` (`shared/ui`): его значение — `ImageFieldValue` (`shared/lib/imageFieldValue`), то есть сохранённое изображение (`savedImage`), выбранный `File` или `null`.
- Одиночное фото с alt (фото контактов, «Моё фото») повторяет `PhotoSlot` бэкенда: `photoSchema` в `shared/api/photo`, поля формы в `shared/lib/photoForm` (`photoFieldsShape` и `refinePhotoAlt` в схеме, `getPhotoChange`, `toPhotoFormValues`) и `PhotoFields` (`shared/ui`), который читает `photo` и `photoAlt` из контекста формы. `EditPhotoForm` (`shared/ui`) — вся форма целиком; фича передаёт ей фото и функцию сохранения (`EditContactPhotoForm`). Сущность только называет свои запросы.
- Упорядоченный список файлов с полями у каждого файла строится на `SortableMediaList` (`shared/ui`), например фото процесса на странице «О сайте». Строки перемещаются перетаскиванием за ручку (dnd-kit) или кнопками со стрелками, поэтому порядок можно изменить и без перетаскивания (WCAG 2.5.7); единственную строку переместить нельзя. Каждую строку можно заменить или удалить, а поля строки выводит владелец списка. Форма хранит строки в `useFieldArray`, ключ строки — `id` поля, и после сохранения сбрасывает их к списку, который вернул сервер. `MediaPicker` и `SortableMediaList` собраны из одних частей: `MediaFieldset` и `FileInput` (`shared/ui/media-field`), `MediaThumbnailButton`, `MediaFileName` и `MediaPreviewDialog` (`shared/ui/media-preview`) и проверки файлов (`getFileRejection`, `useFileDrop` в `shared/lib`).
- То, что не связано между собой, сохраняется по отдельности, без формы: обложка каждой страницы (`PageHeroCard` в `features/edit-page-heroes`) загружается сразу после выбора файла и удаляется после подтверждения в `ConfirmDialog`. Её мутации кладут обложку из ответа сервера в загруженные страницы (`setQueryData`) и перезагружают их только после ошибки.
- Фото попадает в API в два шага: файл уходит в `POST /api/uploads` (`uploadImage` в `shared/api/upload`), а изменение ссылается на него по `uploadId` в JSON-теле. Неудачная загрузка отклоняется с `UploadError`, где указано имя файла; `requestErrorOf` достаёт ошибку запроса для сообщений по статусу.
- Список сохраняется целиком. Форма фото процесса по одному загружает выбранные файлы, затем отправляет весь список одним `PUT` с `ETag` списка, из которого она сделана (`http.getWithETag`, `http.putIfMatch`). Сервер сохраняет всё или ничего и отклоняет с 412 список, изменённый с тех пор, например в другой вкладке. Поэтому форма хранит этот список с его тегом и сбрасывается только к списку, который вернуло сохранение.
- Форма редактирования — это `EditForm` (`shared/ui`): поля, затем `FormActions` с кнопкой сохранения и, пока есть несохранённые изменения, кнопкой отмены. Она сообщает о несохранённых изменениях через `useReportUnsavedChanges` в `UnsavedChangesProvider` (`shared/ui/unsaved-changes`), который лейаут админки выводит один раз вокруг страниц: React Router допускает только один блокировщик одновременно. Пока хоть у одной формы страницы есть несохранённые изменения, уход со страницы сначала спрашивает (`useUnsavedChangesGuard` в `shared/lib`, `ConfirmDialog`).
- Изменение показывает свой результат через query client: его `useMutation` объявляет `meta.feedback` (`MutationFeedback` в `shared/api/queryClient`: `getErrorMessage`, `toastId` и по желанию `successMessage`, по умолчанию «Изменения сохранены»), а приложение показывает тост с ошибкой или успехом (`shared/ui/toast`): `showMutationFeedback` (`app/mutationFeedback.ts`) один раз подписывается на кэш мутаций, поэтому слой данных ничего не знает про UI. Форма только сбрасывает поля после сохранения и оставляет их после ошибки; сохранение, которому нечего отправить, само показывает тост успеха с тем же `toastId`. Ошибки висят, пока их не закроют. У уведомлений одного действия общий `id`, поэтому новый результат заменяет предыдущий.
- Где показывается результат: проверка на клиенте (пустое обязательное поле, тип или размер файла) — под своим полем; ошибка запроса (сервер, соединение, истёкшая сессия) и успешное изменение — в тосте; страница, которая не загрузилась, заменяется своим экраном ошибки; неудачный вход — в форме входа. Тост с ошибкой называет, что не сохранено, например страницу, чья обложка не загрузилась.
- Тексты ошибок запросов лежат в `shared/api/requestErrorMessages`. Изменение, например сохранение или удаление, берёт текст из `getSaveErrorMessage`: истёкшая сессия (`isSessionExpiredError`) даёт `sessionExpiredMessage`, затем действуют тексты самого изменения по статусу (`byStatus`, как их задаёт `getSaveContactLinksErrorMessage`), затем отсутствие соединения и ошибки сервера, затем его `fallback`. Для фото с alt есть `getSavePhotoErrorMessage` (`shared/api/photo`). Загрузка данных и другие запросы используют `getRequestErrorMessage`, который покрывает только отсутствие соединения и ошибки сервера. Ошибки нескольких частей склеиваются через `joinMessages` (`shared/lib`).
- Кнопка только с иконкой — это `IconButton` с `label`, обёрнутая в `Tooltip` с тем же текстом.

### Соглашения React

- Встроенные хуки и API вызываются через пространство имён: `React.useState`, `React.useEffect`, `React.useId`. Именованные импорты из `react` — только для типов.
- Пропсы описываются интерфейсом `interface ComponentNameProps`. `ref` — обычный проп (React 19).
- Статические визуальные значения живут в CSS; React передаёт только данные времени выполнения, например `--active-index`.
- Доступные имена и семантика — часть контракта компонента: у кнопок есть подписи, декоративные элементы скрыты от вспомогательных технологий.

## Бэкенд

Бэкенд разбит на **предметные модули**, как рекомендует [Node.js Best Practices](https://github.com/goldbergyoni/nodebestpractices#1-project-architecture-practices): всё, что относится к одной сущности, лежит в одной папке. Код, который ничего не знает о предметной области, лежит в `shared/`.

```text
backend/src/
├── firebase.ts         точка входа Cloud Function
├── server.ts           приложение Express: общие middleware и роутеры модулей верхнего уровня
├── modules/            по папке на сущность
│   ├── about/          тексты страницы «О себе»; document.ts — документ Firestore, общий с вложенными
│   │   ├── photo/      «Моё фото», подключается роутером about
│   │   └── process-photos/  фото процесса в заданном порядке, подключается роутером about
│   ├── auth/           routes, controller, service, schema, middleware (requireAuth)
│   ├── contacts/       ссылки для связи; document.ts — документ Firestore, общий с photo/
│   │   └── photo/      фото для контактов, подключается роутером contacts
│   ├── health/
│   ├── pages/          страницы публичного сайта и их главные фото (hero)
│   └── uploads/        POST /api/uploads, единственный маршрут с multipart
└── shared/             без знания о предметной области
    ├── config/         env, cookies, cors
    ├── firebase/       клиенты Firebase Admin: app, auth, firestore, storage
    ├── http/           HttpError, entity tags, работа с cookies, типы запроса Express
    ├── images/         обработка изображений через sharp, загрузки, файлы изображений в Cloud Storage, места для фото
    └── middleware/     csrf, content-type, preconditions (If-Match), validation, upload, error
```

- В модуле по файлу на роль: `routes.ts`, `controller.ts`, `service.ts`, `schema.ts`. Запрос проходит путь: маршрут → middleware → контроллер → сервис.
- `shared/` никогда не импортирует `modules/`, это проверяет Biome. Модуль может использовать другой модуль, как `contacts` использует `requireAuth` из `auth`.
- `server.ts` подключает только модули верхнего уровня. Вложенный модуль подключает роутер родителя, как `contacts` подключает `photo`.
- Одиночное фото с alt (фото контактов, «Моё фото») — это `PhotoSlot` из `shared/images/photo.ts`: документ Firestore, поле и папка в Storage. Сервис модуля только называет своё место; сохранение, замена, alt и удаление общие.
- Данные, прочитанные из Firestore, проверяются только на форму (`stored…Schema`): лимиты и форматы проверяются один раз, когда API записывает данные. Поэтому ужесточение правила позже никогда не делает сохранённые данные нечитаемыми. По той же причине схемы ответов описывают форму данных, а не правила запроса.
- Фото загружается один раз (`shared/images/uploads.ts`): оно перекодируется и хранится закрыто в `uploads/{id}` с манифестом, который пишется последним. Изменение, которое его использует, копирует его в новую папку версии своего контента (`publishUpload`) до записи в Firestore, а заменённые файлы и использованная загрузка удаляются последними, поэтому сайт никогда не ссылается на отсутствующие файлы. Неиспользованные загрузки удаляет правило жизненного цикла бакета (`storage.lifecycle.json`). Каждое изменение, которое читает и пишет документ, выполняется в транзакции.
- Коллекция, которую редактируют целиком, например фото процесса, заменяется одним `PUT` всего списка. `GET` возвращает `ETag` сохранённого списка (`entityTag` в `shared/http/etag.ts`); `PUT` требует его в `If-Match` (`requireIfMatch`): 428 без него, 412, если список уже изменился. Элемент называет сохранённый элемент по `id`, новый файл по `uploadId` или оба, чтобы заменить файл; сохранённый элемент, которого нет в списке, удаляется.
- Сессия — это cookie `__session`: другие cookies Firebase Hosting в функцию не передаёт. CSRF-токен — HMAC этой cookie: его выдаёт `GET /api/auth/csrf`, клиент возвращает его в `X-CSRF-Token`. Поэтому у всех вкладок одной сессии один токен, а у новой сессии новый. Входу токен не нужен: сессии ещё нет, а войти может только администратор.
- Глобальные типы Express лежат у своего владельца: `modules/auth/express.d.ts` объявляет `Locals.auth`, `shared/http/express.d.ts` — `Request.file` и `rawBody`.
- Код импортируется через subpath imports (`#modules/auth/service`, `#shared/http/errors`). Файлов-реэкспортов нет.
- Express 5 сам передаёт отклонённые промисы в middleware ошибок, поэтому обработчики не оборачивают код в `try/catch` только ради `next(error)`.
- Переменные окружения читаются через `getEnv()` из `shared/config/env.ts` и проверяются один раз при первом обращении. `CSRF_SECRET` хранится в Secret Manager и читается middleware CSRF.
- Ошибки для клиента выбрасываются как подклассы `HttpError`; middleware ошибок отправляет любую ошибку в формате Problem Details из RFC 9457. Всё остальное логируется и возвращается как общий ответ 500.
- API описан самим кодом: `routes.ts` модуля перечисляет его эндпоинты, а `schema.ts` хранит схемы Zod, которые проверяют запросы и описывают ответы. Контроллеры типизированы схемами ответов (`RequestHandler<Params, Response, Body>`), поэтому обработчик не может отправить ответ другой формы.

## Тесты

- Тесты бэкенда лежат в `backend/tests`, повторяя структуру `src` (`tests/modules/contacts/photo/service.test.ts` тестирует `src/modules/contacts/photo/service.ts`), и запускаются Vitest. Их окружение задано в `backend/vitest.config.ts`.
- В `backend/tests/support` лежат общие помощники: `startTestServer` запускает приложение Express на свободном порту, `adminHeaders` возвращает cookie сессии и CSRF-заголовок вошедшего администратора, `apiImage` возвращает полное изображение для замоканных сервисов, `routeApp` собирает приложение для теста маршрутов: общие middleware, маршруты авторизации и тестируемый роутер. Импортируйте их относительным путём с окончанием `.js`.
- Тесты фронтенда лежат в `front/tests`, так же повторяя структуру `src`, и запускаются Vitest в happy-dom (`front/vitest.config.ts`). Они покрывают логику: схемы форм, изменения, которые отправляет сохранение, функции сохранения, сообщения об ошибках, loader'ы и action'ы маршрутов, хуки. Компоненты пока не тестируются.
- Тесты фронтенда работают с API через MSW: `tests/support/server.ts` перехватывает все запросы, а запрос без обработчика роняет тест. Каждый тест задаёт свои обработчики через `server.use`; `recordRequests` возвращает отправленные запросы по порядку. Другие помощники в `front/tests/support`: `csrfHandler`, `uploadsHandler`, `problem` и `noContent` (`handlers.ts`), `apiImage`, `apiPhoto`, `apiProcessPhoto` и `imageFile` (`images.ts`), `fieldErrors` для схем, `routeArgs`, `formActionArgs` и `thrownResponse` для loader'ов и action'ов.
- Тесты фронтенда импортируют тестируемый модуль по его собственному пути (`@/features/edit-about/model/saveProcessPhotos`), а не через `index.ts` слайса. `vi.mock` остаётся для того, что MSW не заменит: Firebase и тостов.

## Как добавить страницу админки

1. Добавьте путь в `routes` и заголовок в `adminNavigation` в `shared/config/routes.ts`.
2. Создайте `pages/<name>/ui/<Name>Page.tsx` и `pages/<name>/index.ts`.
3. Зарегистрируйте маршрут в `app/router.tsx` с ленивым импортом `@/pages/<name>`.
4. Загрузку данных положите в loader, а сохранение — в action в сегменте `model` страницы. Переиспользуемые действия — в `features`, модели данных и запросы — в `entities`.
