# Архитектура

Как устроен проект и каким соглашениям следует каждое изменение. Правила CSS — в [STYLE_GUIDE.ru.md](STYLE_GUIDE.ru.md).

## Обзор

Монорепозиторий pnpm из трёх пакетов, развёрнутых в Firebase:

| Пакет | Стек | Где работает |
| --- | --- | --- |
| `front` | React 19, React Router (data mode), TanStack Query, TanStack Table, react-hook-form, dnd-kit, Vite, CSS Modules, zod | Firebase Hosting |
| `backend` | Express 5, Firebase Admin, zod | Cloud Functions (`api`, europe-west1) |
| `site` | Astro 7, рендеринг на сервере (адаптер node) | Cloud Functions (`site`, europe-west1) |

Firebase Hosting отдаёт всё с одного домена: админку под `/admin`, `/api/**` из функции `api`, а все остальные пути — из функции `site`, поэтому браузер работает с одним источником (origin) (DEPLOYMENT.md, «What Firebase Hosting serves»).

## Фронтенд: Feature-Sliced Design

`front/src` построен по [Feature-Sliced Design](https://feature-sliced.design). Код разделён на **слои**; слой может импортировать только из слоёв **ниже** себя.

| Слой | Что содержит | Пример |
| --- | --- | --- |
| `app` | Точка входа, роутер, глобальные стили | `app/router.tsx` |
| `pages` | По слайсу на маршрут; собирает виджеты и фичи | `pages/login` |
| `widgets` | Крупные самостоятельные блоки интерфейса | `widgets/admin-layout` |
| `features` | По одному действию пользователя | `features/login`, `features/logout` |
| `entities` | Бизнес-сущности: модель данных, запросы, UI только для чтения | `entities/user` |
| `shared` | Код без знания о предметной области | `shared/ui/button`, `shared/api/http` |

### Слайсы и сегменты

Каждый слой, кроме `app` и `shared`, состоит из **слайсов**, названных по бизнес-понятию в kebab-case. Внутри слайса код сгруппирован по **сегментам**:

| Сегмент | Назначение |
| --- | --- |
| `ui` | Компоненты и их CSS Modules |
| `model` | Состояние, хуки, loader и action маршрутов, схемы |
| `api` | Запросы к бэкенду или Firebase |
| `lib` | Чистые вспомогательные функции |

```text
features/login/
├── api/        createSession, signInWithFirebase
├── lib/        getLoginErrorMessage
├── model/      login, loginSchema
├── ui/         LoginForm.tsx, LoginForm.module.css
└── index.ts    публичный API
```

### Правила импортов

Проверяются dependency-cruiser (`front/.dependency-cruiser.mjs`, запускается в `pnpm check` и в CI). Он проверяет разрешённые пути, поэтому правила одинаково действуют для `@/` и относительных импортов:

- Слайс импортируется только через свой публичный `index.ts`: `@/features/login`, а не `@/features/login/model/login`.
- Слой импортирует только из нижних слоёв: `features` может использовать `entities` и `shared`, но не `widgets` и не `pages`.
- `app` не импортирует никто.
- Внутри одного слайса импорты относительные (`../model/login`). Между слайсами и слоями — через алиас `@/`. Это соглашение, оно не проверяется.
- Слайсы одного слоя не импортируют друг друга. Общее опускается на слой ниже (`isSessionExpiredError` нужен нескольким фичам, поэтому лежит в `shared/api`).
- Модули не импортируют друг друга по кругу.

В `shared` слайсов нет. У каждого компонента `shared/ui` свой публичный `index.ts` (`@/shared/ui/button`). `shared/api`, `shared/config` и `shared/lib` импортируются по файлам (`@/shared/api/http`) намеренно: общий index заставил бы каждый чанк, которому нужен HTTP-клиент, загружать ещё и Firebase.

### Именование

- Папки слайсов и компонентов `shared/ui`: kebab-case (`admin-layout`, `password-input`).
- Файлы компонентов: PascalCase, один компонент на файл, CSS Module рядом (`LoginForm.tsx`, `LoginForm.module.css`).
- Остальные файлы: camelCase, по смыслу содержимого (`getCurrentUser.ts`, `toast.ts`, `loginRoute.ts`).
- Компоненты страниц заканчиваются на `Page` (`GalleryPage`).

### Маршруты и данные

- Пути и заголовки навигации админки заданы один раз в `shared/config/routes.ts`.
- `app/router.tsx` сопоставляет пути со страницами, которые загружаются лениво.
- Данные загружаются через loader React Router, а не через эффекты. Action используется только для изменения, после которого открывается другая страница:
  - маршрут лейаута админки вызывает `requireSession` (`entities/user`) один раз, при входе в админку (`shouldRevalidate: () => false`); на 401 он перенаправляет на `/admin/login?redirectTo=…`, и этот редирект важнее упавшего loader страницы. Любой другой сбой — ошибка, а не повод входить заново. Большинство загрузок страниц — публичные GET, поэтому истёкшую позже сессию находит следующее изменение: его toast сообщает об истёкшей сессии (`sessionExpiredMessage`);
  - внутри админки `useSessionUser()` возвращает текущего пользователя;
  - у страницы входа свои loader и action в `pages/login/model/loginRoute.ts`;
  - выход — это `<Form method="post">` на action `/admin/logout` (`features/logout`). Если сессия могла остаться (нет связи, запрос отклонён), action показывает тост с ошибкой и возвращает на страницу, с которой отправлена форма. После ошибки сервера он сначала спрашивает `/auth/me`: сервер мог очистить cookie и не суметь только отозвать сессию, а мог ответить прокси, и тогда запрос до сервера не дошёл;
  - данные сервера хранятся в кэше TanStack Query (`queryClient` в `shared/api/queryClient.ts`). Сущность отдаёт каждый запрос как query options (`contactLinksQuery` в `entities/contacts`). Фоновых перезапросов нет, кроме переводов, которые меняет сам переводчик: остальные данные меняет только админка;
  - раздел редактирования загружает свой ресурс заново при каждом входе: его loader вызывает `loadFresh` (`shared/api/pageData`) прямо в `routes.ts` страницы. Переход ждёт данные до секунды, поэтому при быстрой загрузке скелетона нет, а при медленной страница открывается со скелетоном. Раздел ждёт данные в `AwaitPageData`, читает их через `useSuspenseQuery` и передаёт форме. Запросы не отменяются: начатый запрос доходит до конца, даже если страницу покинули;
  - таблица только показывает данные, поэтому её loader вызывает `loadCached`: при возврате сразу виден кэш, без скелетона, а свежие данные заменяют его, когда придут. Данные, устаревшие после изменения, не показываются: страница ждёт их, как и форма;
  - форма остаётся на странице, поэтому сохраняет в обработчике отправки react-hook-form (`EditContactLinksForm`) через хук мутации (`useSaveContactLinks`). Мутация отправляет изменения и кладёт сохранённое сервером в кэш (`setQueryData`). Затем форма сбрасывается к сохранённым значениям и показывает результат. Пока идёт сохранение, `isSubmitting` блокирует форму;
  - при выходе кэш запросов очищается.
- Каждое изменение несёт CSRF-токен, и вызывающему коду об этом знать не нужно: `http` (`shared/api/http.ts`) запрашивает его через `GET /api/auth/csrf` при первом изменении и дальше использует повторно. Ответ 403 значит, что сессия сменилась, например после повторного входа в другой вкладке: `http` получает новый токен и отправляет изменение ещё раз. Вход отправляется без токена (`withCsrfToken: false`), при выходе токен забывается.
- `PageLoading` — это `HydrateFallback`, который виден, пока выполняются первые loader.
- Корневой маршрут без пути ловит через `ErrorPage` (`pages/error`) любую ошибку, которую не обработал маршрут ниже. Он импортируется сразу, а не лениво, поэтому работает и когда не загрузился чанк.
- Страницы админки вложены в маршрут без пути, у которого `ErrorBoundary` — `AdminPageError` (`widgets/admin-layout`): страница, которая не загрузилась или упала при рендере, заменяется сообщением внутри лейаута, а навигация продолжает работать.

### Формы и обратная связь

- Формы построены на react-hook-form со схемой zod, которая повторяет правила сервера. Текстовые поля (`Input`, `Textarea`) построены на `Field` (`shared/ui`), который отвечает за подпись, подсказку (`hint`), ошибку и рамку; изменённые поля подсвечиваются пропом `isModified`.
- Форма редактирует один ресурс API и сохраняет все свои изменения или ни одного. Если на странице несколько ресурсов, каждый получает свой раздел: дочерний маршрут со своим адресом, loader и формой (`pages/about`: `/admin/about/text`, `/photo`, `/process`). Страница — это маршрут-лейаут, а `TabNav` (`shared/ui`) связывает разделы ссылками, оформленными как вкладки. Переключение раздела — это переход, поэтому несохранённые изменения всегда в открытом разделе, а уход из него сначала спрашивает, как уход с любой страницы.
- Файлы выбираются через `MediaPicker` (`shared/ui`), по одному файлу. Он проверяет тип и размер по переданным правилам (`rules={imageUploadRules}`) и показывает миниатюры, которые открываются в `PreviewDialog`, но ничего не загружает: в форме выбранный `File` хранится и отправляется при сохранении, поэтому на него тоже действуют отмена изменений и защита от ухода со страницы; поле, которое сохраняется само по себе, загружает файл сразу и на это время показывает `isBusy`. Правила загрузки (`imageUploadRules`) и изображение, которое возвращает API (`imageSchema`), лежат в `shared/api/image`. Одно сохранённое изображение в форме, например фото с alt, выбирается через `ImagePicker` (`shared/ui`): его значение — `ImageFieldValue` (`shared/lib/imageFieldValue`), то есть сохранённое изображение (`savedImage`), выбранный `File` или `null`.
- Каждая часть страницы, которую админ сохраняет отдельно, — отдельный ресурс со своими `GET` и `PUT`: `/api/about/text`, `/api/about/photo`, `/api/about/process-photos`. `PUT` заменяет весь ресурс по своему URL (RFC 9110 §9.3.4), а не часть большего. Сама страница (`GET /api/about`) — агрегат только для чтения, чтобы сайт читал её одним запросом.
- Одиночное фото с alt («Моё фото») повторяет `PhotoSlot` бэкенда: `photoSchema` в `shared/api/photo`, поля формы в `shared/lib/photoForm` (`photoFieldsShape` и `refinePhoto` в схеме, `toPhotoFormValues`, `toPhotoBody`) и `PhotoFields` (`shared/ui`), который читает `photo` и `photoAlt` из контекста формы. `photoSlot(path, queryKey)` (`shared/api/photoSlot`) — ресурс с его запросом, а `saveSlotPhoto` отправляет его изменение; сущность только называет своё место (`aboutPhoto` в `entities/about`). `EditPhotoForm` (`features/edit-photo`) — вся форма целиком вместе с сохранением; страница передаёт ей место, фото и подпись.
- Упорядоченный список файлов с полями у каждого файла строится на `SortableMediaList` (`shared/ui`), например фото процесса на странице «О сайте». Строки перемещаются перетаскиванием за ручку (dnd-kit) или кнопками со стрелками, поэтому порядок можно изменить и без перетаскивания (WCAG 2.5.7); единственную строку переместить нельзя. Каждую строку можно заменить или удалить, а поля строки выводит владелец списка. Форма хранит строки в `useFieldArray`, ключ строки — `id` поля, и после сохранения сбрасывает их к списку, который вернул сервер. `MediaPicker` и `SortableMediaList` собраны из одних частей: `MediaFieldset` и `FileInput` (`shared/ui/media-field`), `MediaThumbnailButton`, `MediaFileName` и `MediaPreviewDialog` (`shared/ui/media-preview`) и проверки файлов (`getFileRejection`, `useFileDrop` в `shared/lib`).
- Все сортируемые списки собраны из `shared/ui/sortable`: `SortableList` (сенсоры, вертикальная ось и объявления для скринридера), `useSortableRow`, `DragHandle` и `MoveButtons` для каждой строки, `useSortableRowFocus`, который возвращает фокус на перемещённую или удалённую строку, и `SortableMessages` с текстами под своё существительное («Фото … взято», «Проект … взят»). Из них же собрана форма порядка проектов (`features/edit-projects`).
- Таблица с поиском или сортировкой строится на TanStack Table (headless; разметка — обычная `<table>` с `aria-sort` у сортируемых колонок), например таблица проектов. Что умеет каждая таблица (сортировка по одной колонке, страницы) и `meta` её колонок объявлены один раз, в `dataTableFeatures` (`shared/ui/data-table`); фича типизирует свои колонки как `DataTableColumn<TItem>`; поле поиска — `SearchInput` (`shared/ui`). Поиск, сортировка и страница хранятся в адресе (`?q=…&sort=title.asc&page=2`), поэтому при возврате к таблице вид сохраняется. Поле поиска держит набранный текст у себя и пишет его в адрес после паузы (`useTableSearch`): смена адреса асинхронная, и привязанное к нему поле теряло бы каретку и буквы. Длинная таблица показывает по 50 строк; смена одних только параметров адреса ничего не загружает заново (`revalidateUnlessOnlySearch` в `shared/lib`). Отсортированная таблица никогда не меняет порядок элементов: порядок на сайте редактируется в отдельной форме.
- Список фото с alt, например фото процесса, фото проекта или слайд-шоу контактов, — это `PhotoListField` (`shared/ui`) на поле `photos` своей формы. В `shared/lib/photoListForm.ts` лежат его строки (сохранённое фото или новый файл), их схема и `toPhotoListItems`, который загружает выбранные файлы и собирает список, который заменяет API. `disabled` оставляет список как есть, пока форма показывает вместо него другое, как галочка «Показывать фото из галереи» у слайд-шоу контактов.
- То, что не связано между собой, сохраняется по отдельности, без формы: обложка каждой страницы (`PageHeroCard` в `features/edit-page-heroes`) загружается сразу после выбора файла. Каждая карточка читает свою обложку (`pageHeroQuery`); загрузка кладёт обложку из ответа сервера в кэш (`setQueryData`), а ошибка загружает её заново.
- Фото попадает в API в два шага: файл уходит в `POST /api/uploads` (`uploadImage` в `shared/api/upload`), а изменение ссылается на него по `uploadId` в JSON-теле. Неудачная загрузка отклоняется с `UploadError`, где указано имя файла; `requestErrorOf` достаёт ошибку запроса для сообщений по статусу.
- Компоненты `shared/ui` не читают данные и ничего не сохраняют: они получают всё через пропсы или контекст формы. Форма и таблица фичи только собирают части: колонки таблицы лежат в своём файле (`worksColumns`), ячейки — в своих компонентах, правка строки и подтверждение — в хуках.
- Удаление, которое нельзя отменить, сначала спрашивает в `ConfirmDeleteDialog` через `useConfirmation` (`shared/lib`): строка таблицы всегда, сохранённое фото списка всегда (`SortableMediaList`, `isSaved`), элемент списка — пока его называют работы. То, что форма только убирает до сохранения, например работу из коллекции, вопроса не требует: «Отменить» вернёт её.
- Каждое изменение условное (RFC 9110 §13.1.1). Ресурс приходит со своим `ETag` (`http.getWithETag`, как `Tagged<T>`), а изменение отправляет его обратно в `If-Match` (`http.putIfMatch`); ресурс, изменённый с тех пор, например в другой вкладке, сервер отклоняет с 412. Форма хранит ресурс, из которого сделана, с его тегом и сбрасывается только к тому, что вернуло сохранение, с новым тегом; за это во всех формах отвечает `useSavedForm` (`shared/ui/edit-form`). После 412 изменения остаются в форме, а тост просит обновить страницу (`conflictMessage` в `getSaveErrorMessage`, если у изменения нет своего текста для 412): администратор у сайта один, поэтому конфликт бывает только с его же другой вкладкой. Удаление из таблицы (`http.deleteResource`) отправляет `If-Match: *`: у строк таблицы нет тегов, а строка называет ресурс по названию. Удалённый ресурс отвечает 204 без тега. Новый элемент коллекции, например проект, создаётся через `http.putIfNoneMatch` под id, который форма выбирает один раз: если попытка создала его, но ответ потерялся, следующая получает 412 и не создаёт второй. Сохранённый элемент она не перезаписывает — его могли изменить в другой вкладке: форма показывает тост и открывает сохранённое. Список сохраняется целиком: форма фото процесса по одному загружает выбранные файлы (`uploadImage` час использует загрузку файла повторно, поэтому повторное сохранение не отправляет его снова), затем отправляет весь список одним `PUT`, который сервер сохраняет целиком или не сохраняет вовсе.
- Форма с переводами оборачивается в `LanguageForm` (`features/edit-translations`), который переключает страницу между русским и формой каждого языка. Правка переводов — отдельная фича, а фичи не импортируют друг друга, поэтому страница передаёт форме проп `languageForm` (`LanguageFormSlot` из `entities/translation`). Каждый язык сохраняется сам по себе и только изменёнными текстами. Имена переводов на сервере собраны в `translationResources`. Тексты приходят из `translationsQuery`: он никогда не считается свежим, поэтому форма читает его заново при открытии, и перечитывается каждые две секунды, пока работает переводчик; сохранение самого ресурса запрашивает новое чтение, так как его тексты могли уйти переводчику; сохранение отменяет идущие чтения, иначе они вернули бы старые тексты.
- Форма редактирования — это `EditForm` (`shared/ui`): поля, затем `FormActions` с кнопкой сохранения и, пока есть несохранённые изменения, кнопкой отмены. Она сообщает о несохранённых изменениях через `useReportUnsavedChanges` в `UnsavedChangesProvider` (`shared/ui/unsaved-changes`), который лейаут админки выводит один раз вокруг страниц: React Router допускает только один блокировщик одновременно. Пока хоть у одной формы страницы есть несохранённые изменения, уход со страницы сначала спрашивает (`useUnsavedChangesGuard` в `shared/lib`, `ConfirmDialog`). Переход, который делает само сохранение, например открытие проекта после создания, сначала вызывает `useAllowNextNavigation` с этим путём: guard узнаёт, что изменения сохранены, только при следующем рендере.
- Изменение показывает свой результат через query client: его `useMutation` объявляет `meta.feedback` (`MutationFeedback` в `shared/api/queryClient`: `getErrorMessage`, `toastId` и по желанию `successMessage`, по умолчанию «Изменения сохранены»), а приложение показывает тост с ошибкой или успехом (`shared/ui/toast`): `showMutationFeedback` (`app/mutationFeedback.ts`) один раз подписывается на кэш мутаций, поэтому слой данных ничего не знает про UI. Форма только сбрасывает поля после сохранения и оставляет их после ошибки; сохранение, которому нечего отправить, само показывает тост успеха с тем же `toastId`. Ошибки висят, пока их не закроют. У уведомлений одного действия общий `id`, поэтому новый результат заменяет предыдущий.
- Где показывается результат: проверка на клиенте (пустое обязательное поле, тип или размер файла) — под своим полем; ошибка запроса (сервер, соединение, истёкшая сессия) и успешное изменение — в тосте; страница, которая не загрузилась, заменяется своим экраном ошибки; неудачный вход — в форме входа. Тост с ошибкой называет, что не сохранено, например страницу, чья обложка не загрузилась.
- Тексты ошибок запросов лежат в `shared/api/requestErrorMessages`. Изменение, например сохранение или удаление, берёт текст из `getSaveErrorMessage`: истёкшая сессия (`isSessionExpiredError`) даёт `sessionExpiredMessage`, затем действуют тексты самого изменения по статусу (`byStatus`, как их задаёт `getSaveContactLinksErrorMessage`), затем отсутствие соединения и ошибки сервера, затем его `fallback`. Для фото с alt есть `getSavePhotoErrorMessage` (`features/edit-photo`). Загрузка данных и другие запросы используют `getRequestErrorMessage`, который покрывает только отсутствие соединения и ошибки сервера. Ошибки нескольких частей склеиваются через `joinMessages` (`shared/lib`).
- Кнопка только с иконкой — это `IconButton` с `label`, обёрнутая в `Tooltip` с тем же текстом.

### Соглашения React

- Встроенные хуки и API вызываются через пространство имён: `React.useState`, `React.useEffect`, `React.useId`. Именованные импорты из `react` — только для типов.
- Пропсы описываются интерфейсом `interface ComponentNameProps`. `ref` — обычный проп (React 19).
- Статические визуальные значения живут в CSS; React передаёт только данные времени выполнения, например `--active-index`.
- Доступные имена и семантика — часть контракта компонента: у кнопок есть подписи, декоративные элементы скрыты от вспомогательных технологий.
- Поддерживаемые браузеры — [Baseline Widely available](https://web.dev/baseline), цель сборки Vite по умолчанию. Более новый API используется только после проверки, как View Transition при смене темы (`'startViewTransition' in document`); полифиллов нет.

## Публичный сайт: Astro

`site` — публичный сайт на [Astro](https://astro.build) с рендерингом на сервере: каждая страница приходит к поисковикам и в карточки ссылок полным HTML. Папки следуют соглашениям документации Astro; сам Astro требует только `src/pages`.

```text
site/src/
├── pages/            маршруты; тонкие, только собирают блоки
├── layouts/          каркас страницы: <html>, <head>, шапка и подвал
├── components/
│   ├── ui/           примитивы дизайн-системы
│   ├── controls/     переключатели для посетителя
│   └── blocks/       части, из которых собираются страницы
├── styles/           токены дизайна, брейкпоинты, темы
├── actions/          то, что отправляет посетитель, например форма рассылки; выполняется на сервере
└── lib/              код без разметки: запросы, языки, форматирование
```

Папка импортирует только из папок ниже: `pages → layouts → blocks → controls → ui → lib`; `styles` доступны любой разметке. `actions` импортируют только `lib`: браузер посетителя никогда не обращается к API, поэтому форма отправляется в своё действие (Astro Actions), которое работает и без JavaScript и проверяет данные через zod до запроса к API. dependency-cruiser не читает файлы `.astro`, поэтому правило проверяет Biome через `noRestrictedImports` (переопределения `site/src/...` в `biome.json`), одинаково для относительных импортов и `@/`.

### Языки

- У сайта те же 26 языков, что у бэкенда (`lib/i18n/languages.ts`; тест следит, чтобы списки совпадали), и каждая страница живёт под кодом своего языка: `/en/`, `/pl/contact`. `<html>` называет вариант, на котором тексты (`pt-BR`, `zh-Hans`), и ставит `dir="rtl"` для арабского.
- Страницы рендерятся по запросу (`output: "server"`, адаптер node в режиме standalone, его оборачивает функция `site` в `site/firebase.js`), поэтому правка в админке видна в пределах минуты, пока CDN хранит страницу.
- Корень `/` переадресует на лучший язык браузера (`Accept-Language`, по весам; `de-AT` находит `de`), иначе на английский. Переадресация у каждого посетителя своя, поэтому никогда не кэшируется. Язык, выбранный переключателем, к следующему визиту не запоминается: Firebase Hosting пропускает к функциям только cookie `__session`, а её занимает сессия админки (docs/TODO.md, «Запоминание выбранного языка»).
- Тексты интерфейса лежат в `lib/i18n/messages/<язык>.json`; `en.json` — источник, а `t(language, key)` типизирована по его ключам. Ещё не переведённый текст показывается по-английски. Контент из админки переводит бэкенд.
- Новый текст: добавить ключ в `en.json`, запустить `pnpm --filter site i18n:translate` и прочитать diff. Скрипт отправляет в DeepL только новые тексты и тексты, чей английский изменился, поэтому перевод, исправленный руками, остаётся; `translatedFrom.json` хранит английский, с которого сделан каждый перевод. Тест следит, чтобы у каждого языка были ключи английского.
- Diff читать перед коммитом: DeepL сказано, что сайт принадлежит одному человеку (`context` в скрипте), но в некоторых языках он всё равно делает из «Get in touch» «Свяжитесь с нами» и даёт «the artist» род. Одно слово «About» из меню он превращает в голый предлог («Über», «O») или «О нас», а «Process» — в процедуру («Ablauf», «Procedura»): на этом сайте это «Обо мне» и процесс работы художника. «Take me home» он понимает как дорогу к дому («Portami a casa», «带我回家»): это главная страница. Вежливая просьба выходит как «мы просим» («Kérjük», «Prašome», «Vă rugăm»), а «Спасибо» и «Я напишу» в португальском и хинди получают род говорящего: такие фразы перестраиваются без него. Такой текст исправляется руками в файле языка, а в английском не должно быть слов, которым нужен род.
- Заголовок на любом языке стоит в одну строку своей колонки: переводить его одним-двумя словами (Kontakt, Contacto), как этот раздел называют сайты на этом языке. Более длинный переносится на две строки и ломает пропорции блока. После такой правки проверить страницу на всех языках.

### Поисковики и карточки ссылок

- `BaseLayout` принимает `path` страницы, её `title` (кроме главной) и `description`, которое берётся из текстов самой страницы и обрезается примерно до 160 символов: отдельного описания художница не пишет. Без описания тег не выводится, и поисковик цитирует саму страницу. Через `PageMeta` он пишет заголовок, описание, канонический адрес, страницу на каждом языке (`hreflang`, английский — как `x-default`) и теги Open Graph для карточки ссылки.
- `robots.txt` и `sitemap.xml` — эндпоинты в `pages/`. Sitemap перечисляет пути из `lib/site/pagePaths.ts` на каждом языке: новая страница добавляет туда свой путь. Поисковикам закрыт только `/api/`; админка для них открыта, чтобы они прочитали её `noindex`.
- Абсолютные адреса строятся из `SITE_URL` (схема env Astro в `astro.config.ts`). Astro вшивает его при сборке, поэтому без него сборка падает. Локально он в `site/.env` (см. `site/.env.example`).

### Данные

- Страница читает данные на сервере через `getJson(path, schema, { language })` (`lib/api/`): ресурс API на языке страницы (`?lang=`), проверенный zod-схемой, которой владеет страница, как это делают сущности админки. Браузер посетителя к API не обращается. Адрес API — `API_URL`, Astro проверяет его так же, как `SITE_URL`.
- API должен ответить за 5 секунд, иначе страница сдаётся. Ресурс, которого у API нет (`isNotFound`), делает страницу 404: `return Astro.rewrite("/404")`. Любая другая ошибка, включая ответ неожиданной формы, выбрасывается и становится страницей 500. Обе страницы ошибок говорят на языке пути и помечены `noindex`.
- Публичные чтения бэкенда учатся `?lang=` по одному ресурсу, вместе со страницей, которой он понадобился первым; у контактов он есть.
- Картинку API показывает `Picture` (`components/ui`): AVIF, иначе WebP, из файлов всех ширин (`srcset`), с `sizes`, которые знает страница. `priority` получает только самая большая картинка первого экрана, чтобы она грузилась раньше остальных. У `deferred` картинки файлы лежат в data-атрибутах, пока её не загрузит скрипт (`loadDeferredImages` в `lib/images`): картинка в поле зрения, например слайд под другим, загрузилась бы сразу, даже ленивая.
- Все слайдеры сайта построены на [Embla Carousel](https://www.embla-carousel.com) с её плагинами, а не написаны вручную. `Slideshow` (`components/ui`) — фото, которые сами медленно сменяют друг друга затуханием (Fade, Autoplay) и, пока показаны, приближаются на 4% (эффект Кена Бёрнса на CSS; без него при `prefers-reduced-motion`): 5 с на фото, ждёт, пока над ним указатель, листается свайпом и не играет при `prefers-reduced-motion`. Слайд не в поле зрения — `inert`; загружены показанный и следующий, остальные ждут (`deferred`). Форму задаёт его рамка через `class`.

### Страницы

- Пока у страниц нет hero, страница называет себя скрытым от глаз `<h1>` (`VisuallyHidden`), а её собственный заголовок — `<h2>`; `<h1>` заберёт hero.
- Иконки — линейные рисунки из [Lucide](https://lucide.dev) (лицензия ISC), по файлу на иконку в `components/ui/icons`, на рамке `Icon.astro`, которая прячет их от скринридеров: ссылку называет текст рядом.

## Бэкенд

Бэкенд разбит на **предметные модули**, как рекомендует [Node.js Best Practices](https://github.com/goldbergyoni/nodebestpractices#1-project-architecture-practices): всё, что относится к одной сущности, лежит в одной папке. Код, который ничего не знает о предметной области, лежит в `shared/`.

```text
backend/src/
├── firebase.ts         точка входа Cloud Function
├── server.ts           приложение Express: общие middleware и роутеры модулей верхнего уровня
├── modules/            по папке на сущность
│   ├── about/          вся страница «О себе» для сайта; document.ts — документ Firestore, общий с вложенными
│   │   ├── text/       тексты: schema.ts и resource.ts
│   │   ├── photo.ts    «Моё фото», место для фото, подключается роутером about
│   │   └── process-photos/  фото процесса в заданном порядке, подключается роутером about
│   ├── auth/           сессия и её cookie, CSRF-токены, protectChanges, requireAuth
│   ├── contacts/       вся страница контактов для сайта; document.ts — документ Firestore, общий с вложенными
│   │   ├── links/      ссылки для связи: schema.ts и resource.ts
│   │   └── slideshow/  фото слайд-шоу или галерея вместо них, подключается роутером contacts
│   ├── currencies/     курсы валют к доллару, задаются вручную
│   ├── gallery/        routes.ts подключает всё вложенное под /api/gallery
│   │   ├── collections/ коллекции, каждая в своём документе Firestore с обложкой и годами
│   │   ├── colors/     цвета, один список по алфавиту
│   │   ├── intro/      текст над работами
│   │   ├── materials/  материалы, один список по алфавиту
│   │   ├── palettes/   палитры (пастельная, яркая…), один список по алфавиту
│   │   ├── sections/   разделы, каждый в своём документе Firestore вместе с подразделами
│   │   └── works/      работы, каждая в своём документе Firestore; representation.ts — что отдаёт API (размер в см и дюймах), prices.ts — цены по курсам, references.ts — на что ссылается работа, order.ts и visibility.ts — как работы выводятся списком
│   ├── health/
│   ├── newsletter/     POST /api/newsletter/subscribers: подписка посетителя; ответ одинаковый для нового и известного адреса
│   ├── originals/      GET /api/originals, загруженные файлы, только для админа
│   ├── pages/          страницы публичного сайта и их главные фото (hero)
│   ├── projects/       проекты, каждый в своём документе Firestore, и их порядок
│   │   └── intro/      текст над проектами
│   └── uploads/        POST /api/uploads, единственный маршрут с multipart
└── shared/             без знания о предметной области
    ├── config/         env, cors
    ├── firebase/       клиенты Firebase Admin: app, auth, firestore, storage; documentResource
    ├── http/           HttpError, entity tags, Problem Details, общие роутеры (ресурс-документ, место для фото), типы запроса Express
    ├── images/         обработка изображений через sharp, загрузки, хранимые изображения, сохранение с файлами, места для фото, списки фото
    ├── middleware/     content-type, preconditions (If-Match), validation, upload, error
    └── text/           названия: сравнение без учёта регистра, сортировка по русскому алфавиту
```

- В модуле по файлу на роль: `routes.ts`, `controller.ts`, `service.ts`, `schema.ts`. Запрос проходит путь: маршрут → middleware → контроллер → сервис.
- Данные, которые сайт читает целиком, а админ заменяет целиком и которые лежат в одном документе, — это `documentResource` (`shared/firebase/document-resource.ts`): тексты-вступления, цвета, материалы и палитры, курсы, тексты «О себе», ссылки контактов. В таком модуле только `schema.ts` и `resource.ts`, который говорит, где лежат данные; его маршруты — `documentResourceRouter(resource, bodySchema)` (`shared/http/document-resource-router.ts`). Изменение заменяет только поля ресурса (`mergeFields`), поэтому остальное содержимое документа не меняется.
- `shared/` никогда не импортирует `modules/`, это проверяет Biome. Модуль может использовать другой модуль, как `originals` использует `requireAuth` из `auth`, но никогда его `service.ts`: то, что нужно другим, например где лежат документы и как они читаются (`document.ts`), лежит в отдельном файле.
- `server.ts` подключает только модули верхнего уровня. Вложенный модуль подключает роутер родителя, как `contacts` подключает `links`. Место для фото подключается как `photoSlotRouter(aboutPhoto)` (`shared/http/photo-slot-router.ts`). В `modules/` только ресурсы API; роутер, который подключают разные модули, лежит в `shared/http`.
- Каждая часть страницы, которую админ сохраняет отдельно, — отдельный ресурс со своими `GET` и `PUT`: `/api/about/text`, `/api/about/photo`, `/api/about/process-photos`. `PUT` заменяет весь ресурс по своему URL (RFC 9110 §9.3.4), а не часть большего. Сама страница (`GET /api/about`) — агрегат только для чтения, чтобы сайт читал её одним запросом.
- Одиночное изображение — это `ImageSlot` из `shared/images/slot.ts`: документ Firestore, поле, схема того, что хранит поле, и папка в Storage. Заполнение и замена места общие. Главное фото страницы хранит только изображение; фото с alt («Моё фото») — это `PhotoSlot` из `shared/images/photo.ts`, который добавляет alt и его изменение. Модуль только называет своё место (`modules/about/photo.ts`).
- Данные, прочитанные из Firestore, проверяются только на форму (`stored…Schema`): лимиты и форматы проверяются один раз, когда API записывает данные. Поэтому ужесточение правила позже никогда не делает сохранённые данные нечитаемыми. Zod работает только с тем, что приходит извне: с телами запросов и хранимыми данными. То, что отдаёт API, описано обычными типами TypeScript в `schema.ts`.
- Фото загружается один раз (`shared/images/uploads.ts`): оно перекодируется и хранится закрыто в `uploads/{id}` с манифестом, который пишется последним. Изменение, которое его использует, копирует его в новую папку версии своего контента (`publishUpload`) до записи в Firestore, а заменённые файлы удаляются последними, поэтому сайт никогда не ссылается на отсутствующие файлы. Этот порядок записан в одном месте, `saveWithImages` (`shared/images/saving.ts`): сервис копирует файлы и пишет внутри него, а при ошибке копии удаляются. Загрузки, использованные или нет, удаляет правило жизненного цикла бакета (`storage.lifecycle.json`) через сутки после создания: использованная остаётся, чтобы изменение, повторённое после потерянного ответа, могло на неё сослаться. Каждое изменение, которое читает и пишет документ, выполняется в транзакции.
- Каждое изменение контента условное. `GET` ресурса возвращает `ETag` того, что он отдаёт (`entityTag` в `shared/http/etag.ts`): любое изменение ответа, например удалённый материал, на который ссылается работа, или дата сохранения, меняет тег, поэтому сильный 304 никогда не устаревший; изменение сверяет `If-Match` с тем же представлением (RFC 9110 §8.8.3; у пустого места для фото это `null`); `PUT` и `DELETE` требуют его в `If-Match` (`requireIfMatch`): 428 без него, 412, если ресурс уже изменился (`assertIfMatch` в той же транзакции, что и запись). Ответ на изменение несёт новый `ETag`. Коллекция, которую редактируют целиком, например фото процесса, заменяется одним `PUT` всего списка: элемент называет сохранённый элемент по `id`, новый файл по `uploadId` или оба, чтобы заменить файл; сохранённый элемент, которого нет в списке, удаляется. Фото такого списка — фото процесса, проекта или слайд-шоу контактов — сохраняет `preparePhotoList` (`shared/images/photo-list.ts`). Фото в теле изменения — `{ alt, uploadId? }` (`photoBodySchema`): без `uploadId` файл остаётся, меняется только alt. Отдельный ресурс возвращается как есть, без обёртки; список — объектом с именованным массивом (`{ works: […] }`).
- Переводы хранятся отдельно от своего ресурса, в `translations/{resource}`, поэтому переводчик никогда не меняет `ETag` открытой формы. Сохранение записывает русские тексты в своей же транзакции (`saveSources`), затем `requestTranslations` ставит ресурс в очередь, а функция `translate` (`modules/translations/worker.ts`) делает недостающее. В `shared/i18n` лежит только то, что нужно сохранениям других модулей; команды админки, воркер и DeepL находятся в `modules/translations`. Статус текста следует из оригинала, сохранённого вместе с ним, поэтому у задачи нет своего состояния: ручная правка сама не заменяется, а текст, запрошенный заново, остаётся, пока не появится новый.
- Публичный `GET`, который читает сайт, принимает язык своей страницы в `?lang=` (`languageQuerySchema` в `shared/i18n/language-query.ts`, проверяет `validateQuery`; неизвестный язык даёт 400 с именем `parameter`); без него тексты приходят на русском. Сервис читает переводы своего ресурса рядом с ним (`readTranslations`) и выбирает каждый текст через `translatedText` (`shared/i18n/translated-text.ts`): перевод, даже сделанный со старого оригинала, иначе английский, иначе русский текст.
- `PATCH /api/translations/:resource/:language` — единственное изменение без `If-Match`: переводчик меняет ресурс в любой момент, и его тег отклонял бы каждое сохранение. Запрос называет только изменённые тексты, а каждая правка называет оригинал, с которого написана, поэтому правка старого оригинала показывается как устаревшая. Две вкладки, правящие один и тот же текст, перезаписывают друг друга: побеждает последняя.
- Коллекция, элементы которой редактируют по одному, например проекты, хранит каждый элемент в своём документе Firestore по `/:id`. Клиент сам выбирает id нового элемента (UUID) и создаёт его через `PUT` с `If-None-Match: *` (201); если id уже занят, сервер отвечает 412, поэтому создание, повторённое после потерянного ответа, не создаёт второй элемент. `PUT` с `If-Match` и `DELETE` меняют его. Порядок — отдельный ресурс (`/api/projects/order`, id по порядку), который хранится как `position` в каждом документе; `ETag` элемента не учитывает позицию, поэтому смена порядка не делает открытую форму устаревшей. Даты ставит сервер: `createdAt` — один раз, `updatedAt` — при каждом сохранении элемента, но не при перемещении.
- Коллекцию работы хранит сама работа (`collectionId`). `PUT` коллекции отпускает свои работы и берёт свободные, а работу другой коллекции отклоняет с 422: `If-Match` этой коллекции ничего не говорит о той. Работа переходит в другую коллекцию только через свою форму.
- Скрытая работа (`published: false`) видна только админу. Публичные `GET` работ и коллекций проходят `identifyReader` (`modules/auth/middleware.ts`): без сессии читает посетитель, он получает только опубликованные работы (скрытая — 404, в `workIds` коллекции её нет); с действующей сессией читает админ, он получает все работы в ответе с `Cache-Control: private, no-cache`; закончившаяся сессия — 401. Ответ зависит от cookie, поэтому в нём есть `Vary: Cookie`.
- Каждое изменение проходит `protectChanges` (`modules/auth/middleware.ts`), который `server.ts` ставит перед маршрутами: любому методу, кроме `GET`, `HEAD` и `OPTIONS`, нужны сессия админа и её CSRF-токен, поэтому новый маршрут защищён сам собой. Перед ним подключены только `/api/health`, `/api/auth` и `/api/newsletter`; маршрут админки, добавленный в них, защищает себя сам.
- Сессия — это cookie `__session`: другие cookies Firebase Hosting в функцию не передаёт. CSRF-токен — HMAC этой cookie: его выдаёт `GET /api/auth/csrf`, клиент возвращает его в `X-CSRF-Token`. Поэтому у всех вкладок одной сессии один токен, а у новой сессии новый. Входу токен не нужен: сессии ещё нет, а войти может только администратор.
- Глобальные типы Express лежат у своего владельца: `modules/auth/express.d.ts` объявляет `Locals.auth`, `shared/http/express.d.ts` — `Request.file` и `rawBody`.
- Код импортируется через subpath imports (`#modules/auth/service`, `#shared/http/errors`). Файлов-реэкспортов нет.
- Express 5 сам передаёт отклонённые промисы в middleware ошибок, поэтому обработчики не оборачивают код в `try/catch` только ради `next(error)`.
- Переменные окружения читаются через `getEnv()` из `shared/config/env.ts` и проверяются один раз при первом обращении. `CSRF_SECRET` хранится в Secret Manager и приходит в функцию как переменная.
- Ошибки для клиента выбрасываются как подклассы `HttpError`; middleware ошибок отправляет любую ошибку в формате Problem Details из RFC 9457. Всё остальное логируется и возвращается как общий ответ 500.
- API описан самим кодом: `routes.ts` модуля перечисляет его эндпоинты, а `schema.ts` хранит схемы Zod, которые проверяют запросы, и типы ответов. Контроллеры типизированы ими (`RequestHandler<Params, Response, Body>`), поэтому обработчик не может отправить ответ другой формы.

## Тесты

- `pnpm test` не нужны внешние сервисы. `tests/document-resources.test.ts` проверяет таблицей все ресурсы-документы через настоящий `server`. `tests/integration` работает с настоящими эмуляторами Auth, Firestore и Storage: путь админа через API, транзакции, копирование файлов, два одновременных сохранения. Запуск: `pnpm test:emulators` (нужна Java 21 и свободные порты эмуляторов). `tests/front-rules.test.ts` сверяет правила, которые повторяет фронт, с API. То же выполняется в CI.
- Тесты бэкенда лежат в `backend/tests`, повторяя структуру `src` (`tests/modules/contacts/links/service.test.ts` тестирует `src/modules/contacts/links/service.ts`), и запускаются Vitest. Их окружение задано в `backend/vitest.config.ts`.
- В `backend/tests/support` лежат общие помощники: `startTestServer` запускает приложение Express на свободном порту, `adminHeaders` возвращает cookie сессии и CSRF-заголовок вошедшего администратора, `apiImage` возвращает полное изображение для замоканных сервисов, `routeApp` собирает приложение для теста маршрутов: общие middleware, маршруты авторизации и тестируемый роутер. Импортируйте их относительным путём с окончанием `.js`.
- Тесты фронтенда лежат в `front/tests`, так же повторяя структуру `src`, и запускаются Vitest в happy-dom (`front/vitest.config.ts`). Они покрывают логику: схемы форм, изменения, которые отправляет сохранение, функции сохранения, сообщения об ошибках, loader'ы и action'ы маршрутов, хуки. Компоненты пока не тестируются.
- Тесты фронтенда работают с API через MSW: `tests/support/server.ts` перехватывает все запросы, а запрос без обработчика роняет тест. Каждый тест задаёт свои обработчики через `server.use`; `recordRequests` возвращает отправленные запросы по порядку. Другие помощники в `front/tests/support`: `csrfHandler`, `uploadsHandler`, `problem` и `noContent` (`handlers.ts`), `apiImage`, `apiPhoto`, `apiListPhoto` и `imageFile` (`images.ts`), `fieldErrors` для схем, `routeArgs`, `formActionArgs` и `thrownResponse` для loader'ов и action'ов.
- Тесты фронтенда импортируют тестируемый модуль по его собственному пути (`@/features/edit-about/model/saveProcessPhotos`), а не через `index.ts` слайса. `vi.mock` остаётся для того, что MSW не заменит: Firebase и тостов.

## Как добавить страницу админки

1. Добавьте путь в `routes` и заголовок в `adminNavigation` в `shared/config/routes.ts`.
2. Создайте `pages/<name>/ui/<Name>Page.tsx` и `pages/<name>/index.ts`.
3. Зарегистрируйте маршрут в `app/router.tsx` с ленивым импортом `@/pages/<name>`. Страница, вложенная в другую, задаёт свои хлебные крошки, а страница с главным действием всей страницы — это действие, в `handle` маршрута (`AdminPageHandle` из `widgets/admin-layout`); лейаут показывает их у заголовка страницы, беря их из самого глубокого маршрута, где они заданы.
4. Загрузку данных положите в loader, а сохранение — в action в сегменте `model` страницы. Переиспользуемые действия — в `features`, модели данных и запросы — в `entities`.
