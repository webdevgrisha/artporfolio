# Руководство по стилям фронтенда

Этот документ определяет правила CSS и адаптивной вёрстки проекта. Это живой документ: дополняйте его, когда повторяющаяся проблема приводит к правилу, улучшающему единообразие, читаемость или доступность.

Подход к единицам измерения основан на статье Джоша Комо [The Surprising Truth About Pixels and Accessibility](https://www.joshwcomeau.com/css/surprising-truth-about-pixels-and-accessibility/): используйте относительные единицы, если значение должно учитывать предпочитаемый пользователем размер шрифта, и фиксированные — если не должно.

Подход к пользовательским свойствам основан на [CSS Variables for React Devs](https://www.joshwcomeau.com/css/css-variables-for-react-devs/): CSS-переменные — наследуемые свойства, а не обязательно глобальные константы. Их область видимости должна принадлежать элементу, который определяет их смысл.

Подход к цветам основан на [Color Formats in CSS](https://www.joshwcomeau.com/css/color-formats/): выбирайте формат с учётом читаемости и преобразований и отделяйте семантическое назначение цвета от его значения.

## Приоритеты

При необходимости компромисса соблюдайте порядок:

1. Корректная семантика и доступность.
2. Стабильная вёрстка на поддерживаемых размерах экрана.
3. Понятное разделение ответственности между родителем и дочерним компонентом.
4. Читаемый CSS с предсказуемыми значениями.
5. Визуальное соответствие Figma.

Не воспроизводите хрупкие координаты из Figma, если дизайн можно выразить нормальным потоком, Flexbox или Grid.

## Организация файлов

- Используйте CSS Modules для компонентов и страниц.
- Храните CSS рядом с TSX-файлом компонента.
- В `reset.css` оставляйте только нормализацию браузерных стилей.
- В `globals.css` оставляйте только общепроектные токены (цвета, отступы, размеры шрифта, анимация, слои) и настройки документа.
- `reset.css` и `globals.css` лежат в каскадных слоях `reset` и `base`; CSS Modules остаются вне слоёв, поэтому стили компонентов всегда побеждают независимо от порядка импортов.
- Общие служебные классы вроде `visuallyHidden` хранятся в `styles/utilities.module.css`. Добавляйте утилиту, только когда одно и то же поведение нужно нескольким компонентам.
- Специфичные для функции переменные храните в ближайшем владеющем layout или компоненте.
- Не помещайте значения админ-панели в глобальные стили.

```text
Component/
├── Component.tsx
└── Component.module.css
```

## Ответственность за стили

Родитель отвечает за размещение непосредственных детей. Дочерний компонент — за внутреннюю компоновку и внешний вид.

```css
/* Parent.module.css */
.profile { margin-inline: var(--sidebar-gutter); }

/* Profile.module.css */
.root { display: flex; align-items: center; gap: var(--space-4); }
```

- Передавайте `className`, если родителю нужно разместить переиспользуемый компонент.
- Не задавайте внешние отступы внутри переиспользуемого компонента.
- Не добавляйте обёртку только ради отступа, если достаточно `className`.
- Обёртка оправдана, если отвечает за семантику, обрезку, размер, прокрутку или область Grid.

## Компоновка

- Сначала используйте нормальный поток документа.
- Flexbox — для одномерного выравнивания, Grid — для двумерной или явно колоночной структуры.
- Для расстояния между равноправными соседями используйте `gap`.
- Для прижатия последнего flex-элемента к краю используйте `margin-block-start: auto`.
- Абсолютное и фиксированное позиционирование оставляйте для оверлеев, декоративных слоёв, индикаторов и привязанного к viewport интерфейса.
- Избегайте `calc(100dvh - 282px)`: пусть flex/grid занимают оставшееся пространство.

## Адаптивная стратегия

- Новые макеты по умолчанию создаются mobile-first.
- Добавляйте breakpoint при изменении компоновки, а не ради единичного отличия в пиксель.
- Используйте три документированных диапазона устройств:
  - телефон: меньше `40rem`;
  - планшет: от `40rem`;
  - компьютер: от `75rem` (сайдбар админки становится колонкой).
- Breakpoint задавайте в `rem`, чтобы при увеличенном шрифте компактная компоновка включалась раньше.
- Используйте `clamp()` только для действительно плавно масштабируемого значения.
- Предпочитайте стабильный размер компонента внутри гибкого контейнера.
- Рассуждайте о доступном пространстве, а не о названиях устройств.
- Проверяйте минимальную ширину, каждый breakpoint, ширину сразу после него и широкий desktop.

```css
/* Избегайте избыточной точности. */
font-size: clamp(1.5rem, 3.515625vw, 2.25rem);

/* Предпочитайте простую осмысленную шкалу. */
font-size: clamp(1.5rem, 3.5vw, 2.25rem);
```

Для вручную заданных fluid-коэффициентов используйте не более двух значимых знаков после запятой, если более высокая точность не обоснована.

## Выбор единиц

Для каждого значения спросите: «Должно ли оно увеличиваться вместе с базовым размером шрифта браузера?» Если да — используйте `rem` или `em`; если нет — `px` либо единицу, связанную с layout.

### Типографика

- Размеры шрифта задавайте в `rem`.
- Не меняйте корневой размер шрифта ради удобного пересчёта.
- Используйте `em`, если значение должно зависеть от шрифта компонента.
- Вертикальный ритм текста обычно должен масштабироваться вместе с текстом.

### Layout и отступы

- Не переводите механически все отступы в `rem`.
- Горизонтальные поля страницы обычно не должны расти со шрифтом и отнимать место у текста.
- Отступы, влияющие на читаемость, обычно должны масштабироваться с текстом.
- Для свободного пространства используйте `%`, `fr`, intrinsic sizing и гибкий рост.
- Для экранов высотой с viewport используйте `dvh`.

### Ширина и высота

- Избегайте фиксированных размеров, если требуемый размер определяет контент.
- Для текстовых контролов предпочитайте `min-block-size`, чтобы они могли вырасти при переносе.
- Компонент с текстом может иметь ширину в `rem`, но также должен иметь `max-inline-size: 100%`.
- `px` подходит для физически стабильной геометрии: однопиксельной границы или кадрирования изображения.

### Viewport и media queries

- Используйте `vw`/`dvw` только для значений, зависящих от ширины viewport.
- Не основывайте размер текста только на viewport-единицах.
- Fluid-типографика должна иметь доступные границы в `rem` и проверяться с увеличенным базовым шрифтом.
- Breakpoint задавайте в `rem`: при крупном тексте эффективного пространства меньше.

## Отступы

- Предпочитайте `gap`, `padding` и правила родителя позиционным смещениям.
- Используйте логические свойства: `margin-inline`, `padding-block`, `inset-inline-start`, `inline-size`, `block-size`.
- Каждый отступ берите из системы отступов ниже. Не переносите расстояния из Figma в пикселях.
- Повторяющемуся отступу функции можно дать локальную именованную переменную, которая ссылается на токен шкалы.

### Система отступов

Все отступы — это шаги одной базовой единицы `--space-unit: 0.25rem` (4px). Шкал две:

| Шкала | Токены | Для чего | Меняется по устройству |
| --- | --- | --- | --- |
| Компонентная | `--space-1` … `--space-8` | Внутри компонентов: padding кнопки, расстояние от подписи до поля, от иконки до текста | Нет |
| Раскладки | `--layout-space-4` … `--layout-space-24` | Структура страницы: поля страницы, расстояния между секциями, отступы сайдбара | Да, × `--layout-scale` |

Число в имени токена — это количество базовых единиц: `--space-4` = 4 × 4px = 16px.

Коэффициент раскладки задаётся один раз в `globals.css`:

| Устройство | Диапазон | `--layout-scale` | `--layout-space-4` |
| --- | --- | --- | --- |
| Телефон | меньше `40rem` | 1 | 16px |
| Планшет | от `40rem` | 1.25 | 20px |
| Компьютер | от `75rem` | 1.5 | 24px |

```css
.page {
  /* Сам растёт от телефона к компьютеру, media query не нужен. */
  gap: var(--layout-space-8);
}

.button {
  /* Одинаково на всех устройствах. */
  padding: var(--space-1) var(--space-4);
}
```

Правила:

- Компонент выглядит одинаково на любом устройстве, поэтому использует только `--space-*`.
- Раскладка решает, сколько воздуха вокруг компонентов, поэтому использует `--layout-space-*`.
- Media query для отступа нужен только тогда, когда меняется сама раскладка. Например, поле страницы переходит с `--layout-space-4` на `--layout-space-12`, потому что появляется сайдбар.
- Нужного шага нет? Добавьте его в `globals.css` и в эту таблицу, а не пишите сырое значение.
- Пиксели остаются для физической геометрии, которая не является отступом: рамка в 1px, смещение фокус-рамки, размеры изображений.

Размеры шрифта берутся из фиксированной шкалы `--font-size-sm` … `--font-size-4xl`. Меняйте размер шрифта между устройствами через media query только там, где этого требует дизайн.

## Пользовательские свойства

CSS-переменные наследуются. Объявляйте их на ближайшем общем предке всех потребителей. Глобально храните только настоящие общепроектные токены.

```css
:root {
  --motion-duration-standard: 180ms;
  --motion-easing-standard: cubic-bezier(0.2, 0, 0, 1);
}

.sidebar {
  --sidebar-gutter: var(--layout-space-10);
}
```

Именуйте по назначению: `--sidebar-gutter`, а не `--space-78`. Исключение — токены шкалы вроде `--space-4`: их имя означает шаг системы отступов, а не значение в пикселях.

### Область видимости и ответственность

- Переменная не становится глобальной автоматически.
- Используйте `:root`, только если токен нужен всему приложению.
- Токены функции размещайте на её layout-root, токены компонента — на корне компонента.
- Дочерний компонент может использовать токен родителя, если это намеренная часть layout-контракта.
- Не делайте значение глобальным только ради отказа от класса или правильной локальной декларации.

### Меняйте значение, а не потребителей

Если компоненты разделяют одно семантическое адаптивное требование, меняйте общую переменную один раз. Совпадения чисел для общего токена недостаточно.

### React и runtime-значения

- Статические визуальные значения храните в CSS.
- Передавайте CSS-переменную из React только для runtime-данных: активного индекса, измеренной координаты или пользовательской темы.
- React передаёт данные, CSS отвечает за формулу и transition.
- Доступ к root-переменным через JS — исключение, а не стандарт управления состоянием.

```tsx
const indicatorStyle = { "--active-index": activeIndex } as React.CSSProperties;
```

```css
.indicator {
  transform: translateY(calc(var(--active-index) * var(--item-size)));
}
```

- CSS-переменные не типизированы статически: используйте ясные имена и визуальные тесты.
- Переменная не может быть условием media query.
- Fallback в `var()` нужен только для действительно необязательного значения.
- Не создавайте одноразовую переменную, если она не является осознанным API компонента.

## Цвета

### Семантические токены

- Повторяющиеся цвета оформляйте семантическими переменными.
- Называйте по роли: `--color-text-muted`, а не `--gray-500` в компоненте.
- Палитра может описывать внешний вид, но компоненты должны использовать семантические aliases.
- Одноразовые цвета ассетов оставляйте локальными.

```css
:root {
  --color-text: hsl(0deg 0% 0%);
  --color-text-muted: hsl(0deg 0% 47%);
  --color-surface: hsl(0deg 0% 100%);
  --color-border: hsl(0deg 0% 0%);
}
```

### Форматы

- Используйте современный синтаксис с пробелами.
- Для прозрачности используйте `rgb(r g b / alpha)` или `hsl(h s l / alpha)`, не устаревший `rgba()` с запятыми.
- HSL — читаемый формат для вручную задаваемых sRGB-цветов.
- Hex допустим для очевидных `#000`/`#fff`, импортированных брендовых значений и внешних спецификаций.
- Именованные цвета оставляйте для прототипов, тестов и обучения; исключения — `transparent` и `currentColor`.
- Не копируйте HSB из Figma напрямую в `hsl()`: brightness и lightness различаются.

### Перцептивные и wide-gamut цвета

- Рассмотрите `oklch()` для палитры с визуально равномерными шагами светлоты.
- Не вводите OKLCH только ради чёрного, белого или одного цвета.
- Display P3 используйте как progressive enhancement с sRGB fallback.

### Производные цвета и доступность

- По умолчанию храните полные значения цветов.
- Разделяйте каналы только при реальном runtime-вычислении связанной палитры.
- Для статической палитры предпочитайте явные семантические токены цепочкам вычислений.
- Для полупрозрачного overlay используйте цвет с alpha, а не `opacity` контейнера.
- Проверяйте контраст текста и всех состояний; понятный формат цвета не гарантирует доступность.
- Не передавайте состояние только цветом.
- Проверяйте hover, focus, active, disabled и error на каждой поверхности.

## Селекторы и классы

- Используйте локально понятные имена: `.header`, `.navigationLink`, `.activeIndicator`.
- Избегайте зависимости от глубины DOM и сохраняйте низкую специфичность.
- Descendant-селектор допустим для тесно связанного элемента, например `.avatar img`.
- Не используйте ID и `!important`.
- Состояние выражайте классом, ARIA- или `data-*`-атрибутом.
- Для условных React-классов используйте `clsx`.

## Типографика

- Наследуйте проектный шрифт из глобальных стилей.
- Явно задавайте `font-weight` заголовкам.
- По возможности используйте безразмерный `line-height`.
- `line-height: normal` применяйте только намеренно.
- Защищайте layout от динамического текста с помощью `min-inline-size: 0` и подходящего переноса.

## Взаимодействие и доступность

- Ссылка — для навигации, кнопка — для действия.
- Каждый интерактивный элемент должен иметь видимый `:focus-visible`.
- Hover-only эффекты при необходимости ограничивайте `@media (hover: hover)`.
- Учитывайте `prefers-reduced-motion` через общие токены движения.
- Скрытый drawer должен быть недоступен для указателя и клавиатуры, а не только сдвинут за экран.
- Декоративные изображения получают пустой `alt`.

## Изображения

- Помещайте изображение в контейнер, если форма, обрезка или пропорции принадлежат UI.
- Для кадрирования используйте `object-fit: cover`, для полного отображения — `contain`.
- Резервируйте место размерами или `aspect-ratio`, чтобы избежать layout shift.
- Переиспользуйте ассет, только если подходят его обрезка, разрешение и пропорции.
- Контентные изображения должны постепенно получить responsive sources, современные форматы и lazy loading ниже первого экрана.

## Анимация

- По возможности анимируйте `transform` и `opacity`.
- Не анимируйте тяжёлые для layout свойства, если движение выражается transform.
- Используйте общие duration и easing tokens.
- Анимация должна сообщать об изменении состояния, а не быть только украшением.

## Правила переноса из Figma

- Figma — визуальная спецификация, а не production-код layout.
- Сначала определяйте связи элементов, затем переносите размеры.
- Сохраняйте точную геометрию ассетов и значимую типографику.
- Заменяйте абсолютные координаты нормальным потоком, Flexbox или Grid.
- Не создавайте отступы пробелами в тексте.
- Предпочитайте именованные связи необъяснимым формулам.
- Документируйте оптические корректировки отдельно от геометрического выравнивания.

## Чек-лист ревью

- Семантика компонента корректна.
- Ответственность родителя и ребёнка ясна.
- Нет ненужного абсолютного позиционирования.
- Адаптивное поведение осмысленно на каждом breakpoint.
- Динамический контент переносится без overflow.
- Текст пригоден для использования при zoom 200%.
- Layout работает при базовом размере шрифта браузера не менее 32px.
- Работают клавиатурный focus, hover, reduced motion и скрытые состояния.
- У повторяющихся значений один источник истины.
- Числа читаемы и объяснимы.
- Ассет или компонент не создан повторно без причины.
- Проходят `pnpm check` и сборка фронтенда.

## Развитие руководства

Добавляйте правило, когда одна дискуссия повторяется, ошибка выявляет отсутствующее соглашение, появляется общий паттерн или дизайн-система получает переиспользуемый токен/компонент.

Каждое новое правило должно объяснять причину и содержать короткий пример из проекта.
